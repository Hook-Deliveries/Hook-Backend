SSH access and environment updates

Use this runbook from the operator's Windows PC. Keep secrets in the server environment files only.

1. Connect from Windows Command Prompt

Open Command Prompt on the PC that holds her private key and run:

ssh -o IdentitiesOnly=yes -i "%USERPROFILE%\.ssh\id_ed25519" root@153.92.222.181

At the passphrase prompt, enter the key's passphrase. It is not the VPS password. If SSH asks to trust a host key, verify its fingerprint in Hostinger before accepting it.

2. Switch to the deployment account

sudo -iu deploy
whoami

The result should be deploy. Run project commands only after SSH connects and the remote Linux prompt appears.

3. Open the existing main environment file

cd /home/deploy/hook-backend/deploy
if [ -f .env ]; then nano .env; else echo ".env missing - stop"; fi

This checks that the real file exists before opening Nano. If it reports missing, do not create an empty file; confirm the project path first.

Values to set in both environments

Edit the existing lines; do not add duplicate names. Enter the API key and secret directly in Nano, with screen sharing paused.

CLOUDINARY_CLOUD_NAME=df4f0usnh
CLOUDINARY_API_KEY=(enter privately)
CLOUDINARY_API_SECRET=(enter privately)
CLOUDINARY_UPLOADS_ENABLED=true
CLOUDINARY_UPLOAD_FOLDER=hook
CLOUDINARY_UPLOAD_PRESET=ProfileX
PAYMENT_WEB_ORIGIN=https://app.hook.africa
PUBLIC_WEB_URL=https://app.hook.africa

Save with Ctrl+O, Enter, then Ctrl+X. Check the variables without printing secrets, then apply the main change:

chmod 600 .env
docker compose up -d --force-recreate api-1 api-2 api-3 worker consumer-payments consumer-orders consumer-fulfilment
docker compose ps

Container recreation applies the new values and can briefly interrupt requests. PAYMENT_WEB_ORIGIN is used for hosted payment links. PUBLIC_WEB_URL is documented here but is not currently read by backend code.

Development is a separate checkout. Its expected file is /home/deploy/hook-dev/deploy/.env. Verify the directory and existing file before editing. Do not create it if missing.

Cloudinary checks for main and development

What the code expects

Catalog media uploads are signed and require CLOUDINARY_CLOUD_NAME, CLOUDINARY_API_KEY, and CLOUDINARY_API_SECRET. They do not use the upload preset. The general upload route uses signed uploads when the API key and secret are present; it uses the unsigned preset only when those credentials are absent.

CLOUDINARY_UPLOADS_ENABLED gates production startup validation. CATALOG_SIGNED_MEDIA_ENABLED controls the signed catalog upload route.

Live verification · 10 November 2026

Both main and development environment files were updated and their API, worker, and consumer containers recreated. The running API containers show the requested Cloudinary values and both Hook web URLs. A signed Cloudinary ping from the VPS host returned HTTP 200, confirming the configured credentials. HTTPS requests to api.cloudinary.com from both API containers timed out, while a general HTTPS check from the main API container succeeded. The remaining failure is container-to-Cloudinary API connectivity; an actual media upload is not yet confirmed.

The exact network cause is not identified. Check DNS and outbound routing from each Docker network before changing firewall or Docker settings. Do not treat the env update alone as proof uploads work.

Safe check from each deploy folder

docker compose ps
docker compose exec -T api-1 node -e 'for (const n of ["CLOUDINARY_CLOUD_NAME","CLOUDINARY_API_KEY","CLOUDINARY_API_SECRET"]) console.log(n+": "+(process.env[n]?"set":"missing"))'
docker compose exec -T api-1 node -e 'const h=require("https");const u="https://api.cloudinary.com/v1_1/"+process.env.CLOUDINARY_CLOUD_NAME+"/ping";const q=h.get(u,{auth:process.env.CLOUDINARY_API_KEY+":"+process.env.CLOUDINARY_API_SECRET,timeout:7000},r=>{console.log("Cloudinary HTTP "+r.statusCode);r.resume()});q.on("timeout",()=>q.destroy(new Error("timeout")));q.on("error",e=>console.log("Cloudinary request failed: "+(e.code||e.message)))'

Run the checks separately in main and development. They report presence/status only; never print the env file.

Before touching development

Check that /home/deploy/hook-dev/deploy/.env exists. Inspect only the non-secret isolation settings:

cd /home/deploy/hook-dev/deploy
grep -E '^(COMPOSE_PROJECT_NAME|API_IMAGE|API_PORT|API_BIND|SKIP_NGINX)=' .env

The Compose defaults use project hook, image hook-api, and Nginx ports 80 and 443. If both stacks are running, development must use an independent Compose project and image, a distinct API port, and must not start a second Nginx on the same ports. If unclear, stop and ask the server owner before running Compose.

After isolation is verified, update development

if [ -f .env ]; then nano .env && chmod 600 .env; else echo ".env missing - stop"; fi
docker compose up -d --force-recreate api-1 api-2 api-3 worker consumer-payments consumer-orders consumer-fulfilment
docker compose ps

Run this only from the development deploy directory after confirming the project name, image, port, and Nginx setup are separate from main.

GitHub deploy behavior

A successful CI run on development deploys development; a successful CI run on main deploys production. GitHub does not copy server .env files. Update and verify each server environment separately before relying on a push.

Keep credentials private. Never commit API keys or secrets, paste env contents into chat, or share a screen while editing them. Rotate credentials that have been exposed, then update both server files and recreate their app containers.
